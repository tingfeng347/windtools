# 终端视觉工具调研

调研日期：2026-10-07。范围：面向 `windtools` 首批 2–3 个 Rust 工具的竞争约束与候选方向；工作目录仍为 `windtui`。使用 Tavily 搜索及提取官方仓库 README；未运行竞品、未复现性能数字。下文“官方描述”表示作者声称支持，不能替代本地验证。候选方向均为待用户访谈验证的假设，不是已确定的产品决策。

## 七个主要参照

| 项目 | 官方内容能够支持的事实 | 对 windtools 的约束（分析） |
| --- | --- | --- |
| [CMatrix](https://github.com/abishekvashok/cmatrix) | Matrix 字符雨，可选择同步/异步滚动、速度与颜色。 | 单做字符雨容易成为已有视觉形式的复刻。 |
| [genact](https://github.com/svenstaro/genact) | 无实际工作的活动生成器；有 cargo、Docker、编译、下载等模块；使用 Rust，官方列出 Linux、macOS、Windows、FreeBSD 和 WebAssembly 支持。 | “Rust + 跨平台 + 假装很忙”已经存在；语言本身不是差异。 |
| [cbonsai](https://gitlab.com/jallbrit/cbonsai) | 程序化盆景，支持生长、无限/屏保模式、文字消息、种子与生长进度缓存。 | “会生长的字符植物”和屏保连续性已有直接参照。 |
| [TerminalTextEffects](https://github.com/ChrisBuilds/terminaltexteffects) | Python CLI 与库；可把输入文本变为动画，具有路径、缓动、场景、颜色渐变、事件及多种效果；支持 inline 输出。 | 文本输入→视觉特效已有成熟产品，不能只凭增加特效数量定位。 |
| [tarts](https://github.com/oiwn/tarts) | Rust 终端屏保集合；包括 Matrix、生命游戏、迷宫、boids、3D cube、donut、pipes、fire、plasma 等。 | 与“用 Rust 把经典特效装成工具集”的构想直接重合。README 的高性能措辞未经本次实测。 |
| [termflix](https://github.com/paulrobello/termflix) | Rust 动画播放器；官方列出三平台构建，Braille/半块/ASCII 三种渲染、多级颜色、运行时切换、录制回放、随机种子、性能统计，以及通过 NDJSON 文件或 stdin 控制动画参数。 | “Rust + 多动画 + 真彩色 + 可接外部数据 + 回放”已经有直接参照，通用数据接入不能自动构成差异。页面简介与 README 的动画数量不一致，本调研不以数量比较。 |
| [EcoCore](https://github.com/Hemantabhusal/EcoCore) | Rust 实验项目，把系统活动映射到环境场景；README 列出 Linux CPU/内存/网络/磁盘采样，以 Kitty 图形协议为主后端，强调高端视觉而非广泛兼容，当前有猫咖场景；明确不以显示原始数字为目标。 | “让电脑状态成为有生命的场景”也已有尝试。字符渲染、跨平台和可读数值可能形成不同取舍，但不代表市场空白。 |

## 额外的反证与边界

- [pipes.sh](https://github.com/pipeseroni/pipes.sh) 已提供可定制管道字符的动画屏保，依赖 Bash 4+ 与 ncurses/tput。它适合学习字符造型，不能据此推导跨平台开箱即用。
- [ttfx](https://github.com/omacom/ttfx) 明确定位为 TerminalTextEffects 的 Rust 移植及单静态二进制，官方范围为 Linux/macOS。因此“把 Python 特效改成 Rust”也已有直接项目；其仓库性能表不能直接等同于终端实际帧率或功耗。
- [Taman](https://github.com/harmoneer/taman) 已把 Rust/Ratatui 番茄钟、植物成长、统计、主题、持久化和连续天数结合。因此“专注种树”不能未经进一步调查就作为原创卖点。
- 同轮官方资料核对还包括：[arttime](https://github.com/poetaman/arttime) 把字符画与时钟、计时和模式化时间管理结合；[pomo](https://github.com/Bahaaio/pomo) 有字符画计时字体、暂停恢复、通知与统计；[ttyplot](https://github.com/tenox7/ttyplot) 从 stdin 数值生成实时图表，并提供计数器速率以及实验性 Braille/块字符绘制。这进一步约束了“艺术 + 实用”的宽泛定位：必须落到具体使用流程。

## 可以继续追问的两个首发组合

### A. 可读的字符观测：2 个工具

假设目标用户是经常留一个终端窗格观察开发任务的人；他们既想看见状态，也想让画面有趣。

1. `windtools pulse`：CPU 与内存映射到一幅固定的字符风景，例如风速与水位；始终保留精确值、更新时间、图例。首版只做这两项本机指标与一种视觉场景。
2. `windtools stream`：从 stdin 接收文本行，以流量与错误事件驱动同一视觉语言中的“事件河流”；同时保留最近若干行原文，可暂停查看。首版只支持文本行和显式用户规则，不做通用日志语义分析。

相对取舍：比纯屏保多一层可解释的真实信息；相对 EcoCore 强调字符兼容与读数，相对 termflix 强调开箱即用的数据来源、原文和可追踪事件。**这只是具体产品取舍，尚未证明用户愿意为其替换现有工具。**

范围风险：高吞吐输入要有界缓存；视觉聚合不可伪装成完整日志记录；跨平台指标的语义、采样精度需验证；若继续加入网络、进程管理、历史查询，很快会变成通用监控工具。

### B. 把等待变成有反馈的场景：2 个工具，可选第 3 个

假设目标用户最常遇到的空档是长命令等待和短时专注；他希望一眼知道“还在运行、结束了、失败了”。

1. `windtools wait -- <command>`：只包装用户明确给出的非交互命令，保留输出、退出状态和耗时；运行中播放一幅标志性字符场景，成功/失败有不同收尾。没有真实进度来源时，只显示时间与活动状态，不编造百分比。
2. `windtools focus 25m`：把倒计时映射到同一场景的光线/天气变化，支持开始、暂停和完成；首版只有计时与少量本地记录，不扩成待办系统。
3. 可选 `windtools scene`：独立欣赏该场景，供截图、演示与短时放空；它是已有画面的独立入口，不先建设大而全的屏保库。

相对取舍：与 genact 的假活动区分在真实命令状态；与通用特效引擎区分在完整工作流；与 Taman 区分在视觉主题和“等待/计时共用一个场景”，但差异强度仍需验证。首版最好先完成前两个，不因凑数量添加第三个。

范围风险：命令包装涉及信号转发、退出码、stdout/stderr、子进程清理；若承诺交互式 shell、PTY、后台守护或跨设备通知，成本会迅速扩大。专注工具也需要明确暂停、系统休眠和恢复的时间语义。

## 根据本轮访谈更新的建议

用户已明确首发为一款观赏工具加一款实用工具，统一入口但采用不同风格；风、粒子、山水生成艺术用于观赏工具。字符绘制允许 Unicode，提供纯 ASCII 模式。以上组合保留为候选分析，首发决策以 `docs/design.md` 为准。

后续访谈已选定“风过原野”与本地 TUI 待办清单；本报告中的命令等待、日志观察、专注计时仅保留为调研阶段的候选。特色可以来自具体场景、视觉语言和完成度；已有资料不足以支持“没有竞品”“比它们更快”或“Rust 本身就能形成特色”的结论。
